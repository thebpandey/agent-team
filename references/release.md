# Deployment, recovery, and cleanup

## Integration and preview gates

The project orchestrator owns integration and production release under [project coordination](projects.md). Feature teams hand off branches and evidence; they do not publish independently. Before integrating a feature, inspect its canonical [preview gate](preview.md). A required missing, stale, or unknown approval blocks that feature even when tests pass and standing deployment authority exists. Have the delegated verifier check the combined version in the integration worktree; on its accepting verdict, update main through the established process. Preserve exclusive integration/release ownership across the operation.

Before updating remote main, inspect whether that push itself triggers production deployment. Honor the run's off/batch choice through the established gated process, or report the conflict before pushing. Do not change deployment configuration or silently publish to satisfy integration.

## Standing authorization

Resolve deployment mode through [settings](settings.md) and the [run record](runs.md). Explicit `auto-deploy` authorizes automatic batches for this run using the established target/process. When auto-deploy is inherited from saved defaults, show it in the effective-run summary and continue without a run-specific confirmation. With auto-deploy off, report the integrated result and leave deployment pending; continue authorized development and eligible cleanup without asking a generic deployment or continuation question. Earlier general standing authority does not silently enable this mode. A one-time approval covers the reported release, not future automatic batches.

Reuse the active user's established target and safe rollback authority within its scope. Do not ask again per enabled batch. If target or required authority is missing, prepare a concrete verified release and ask for the missing decision once. Installing the skill or saving a preference grants no unknown destination, purchase, or destructive data permission. Preserve the run's effective setting source, explicit overrides, and target/authority pointers for recovery. Honor enforced approval gates and access controls.

## Batch completed tasks

Count unique completed top-level delivery IDs selected before dispatch, not commits, child tasks, review attempts, or summary epics. Eligible tasks have all required feature/subtask evidence, version-specific preview approval when required, and verified integration into main. They must not already be deployed in the current verified production state. Production/cleanup criteria remain pending until performed; code integration only makes a task eligible. Keep pending IDs in integration order in the active tracker.

`auto-deploy B` enables positive-integer batches; standalone `auto-deploy` uses one. On a start, `auto-deploy` without B uses that run's effective team limit: `start 3 auto-deploy` deploys three completed tasks together, while `start 3 auto-deploy 1` deploys individually. Settings can supply another batch size when deployment is inherited. Batch size is separate from the maximum of six concurrent teams.

Under exclusive release ownership, select the oldest B eligible pending IDs and freeze the exact integrated boundary revision/artifact containing them. A batch of three means three new completed top-level tasks; do not deploy later tasks merely because main advanced while preparing the batch. Have the delegated verifier confirm the actual delta from the deployed revision, including relevant configuration and artifacts; the orchestrator decides on that evidence. Unexpected, unrelated, held, or unverified changes in that delta block submission until scope is resolved. Prior integrated undeployed tasks may be included only after the verifier confirms their IDs, evidence, gates, and target scope; do not skip ancestor changes or fabricate a clean batch by resetting main. If the provider can deploy only latest main, coordinate an established release boundary before advancing it further, or report the limitation. Development may continue in feature worktrees. Do not invent deployment controls or alter the pipeline to bypass the batch rule.

Submit full batches serially as they become ready; development refill is independent. At the end of a finite admitted set, exhaustion of a continuous run's scoped list, or a point where all remaining work is blocked and none can progress, deploy a final nonempty smaller batch automatically under the same gates. For standalone deployment-only runs, the existing eligible set is finite. If more than one full batch is pending, release each full batch first, then the remainder. Do not flush while active development can still fill the batch, on a named team pause alone, during a project pause, or while automatic deployment is held after failure. Never deploy an empty batch or treat lack of observed data as queue exhaustion.

Record batch ID, exact top-level task IDs, boundary revision/artifact, target, intent, and provider operation identity. Mark these IDs deployed only after successful live verification; then handle the next batch and required cleanup. Preserve pending and in-flight batches across pause/resume. A provider success with failed tracking requires tracking repair, not another deployment. A rollback restores the actual deployed task set and reopens affected tasks; it does not count as a successful feature batch.

Before release, the delegated verifier confirms feature-code explanations and relevant MISTAKES.md updates within the existing review; the orchestrator dispatches that check and consumes its evidence rather than inspecting the code itself. Acceptance evidence must cover the important changed user flows on the integrated version. Blocked or simulated checks must not be reported as real end-to-end success. Then have the verifier confirm, and the orchestrator record, that:

1. Requirements and required reviews/checks pass for the exact integrated source and resulting artifact. Identify target environment and release identity. Exclude unrelated uncommitted changes from the artifact.
2. The established deployment process, live health/smoke signals, and a bounded observation window appropriate to the project are known. If absent, establish a small realistic check rather than an elaborate monitoring exercise.
3. A known-good release artifact/revision and supported recovery action are identified. Confirm compatibility with schema, configuration, and external state. For first deployments without a prior release, define safe disabling/removal of the failed new release. Resolve irreversible migration recovery separately before release.

Prefer native deployment health checks and automatic recovery where available. This skill is not a background monitor and cannot guarantee recovery after runtime termination.

## Release once, inspect uncertain outcomes

Deploy the verifier-accepted artifact and capture deployment identity; have the delegated verifier confirm live health plus a representative changed user path on the intended destination. Mark success only when provider state and the verifier's live evidence agree. A build result is not production verification.

If deployment fails before live state changes, preserve the existing release and diagnose. For ambiguous status, inspect deployment/traffic state before retrying. If live checks fail, restore the known-good compatible artifact or approved first-release recovery, then have the delegated verifier confirm recovery. Do not revert schema/data automatically without explicit authority and a known-safe procedure. If recovery fails or would be destructive/unknown, stop further promotions, preserve evidence, report the incident, and request the specific missing decision. Never enter a deploy/rollback loop.

Any failed batch holds further automatic deployments, including a final smaller batch. Use the existing authorized recovery procedure. Independent development may continue when the failure is confined to the deployment service and does not affect its safety. Pause affected development/integration when defective code or a shared integration problem is implicated. Before lifting the deployment hold, record evidence that the cause is resolved and required release checks pass for the candidate artifact. Existing run authority can then resume batches; do not retry with unchanged conditions, clear the hold from a fresh settings read, or demand a new general approval when the existing scope still applies.

After every successful release, including a verified rollback, record outcome, release identity, revision, verification/recovery evidence in the active tracker: Beads when in use, otherwise the canonical TASKS.md. Reopen affected feature tasks after rollback; recovery does not mean the feature was delivered. If tracking fails, retain a local checkpoint and repair the record without redeploying.

## Cleanup after verified integration, independent of deployment

After verified integration, the project orchestrator reclaims eligible stopped, clean task-owned resources even when deployment is off. Required previews, unfinished work and evidence retention still prevent removal. After a release, also finish any remaining eligible cleanup in the same workflow. Repair missing records first; no deployment or redeployment is required merely for cleanup.

The orchestrator confirms, from the bundled cleanup helper's checks and the delegated verifier's recorded evidence, that each non-canonical task worktree's required changes are safely committed, integrated and verified at the recorded revision; it does not inspect the worktree's code itself. Confirm writers/task processes stopped, preserve evidence and resumption notes outside the checkout, inspect tracked/untracked/ignored files, then remove only the clean disposable checkout through normal Git worktree removal. Verify removal and update the active tracker. Never remove the canonical checkout or the checkout containing the tracker or its referenced unarchived evidence. Retain release and rollback records independently of the worktree.

Preserve the main checkout regardless of directory name, unrelated user worktrees, active work, unintegrated changes, failed/rolled-back feature work, and unarchived evidence. Do not force-delete, reset away changes, or delete branches as a substitute for checking. Remove all eligible completed task worktrees, including explicitly adopted ones. Report retained trees with concrete reasons. Free only task-owned resources.

Inventory all feature and child worktrees created or adopted for the integrated team, plus its preview servers, task processes, logs, temporary files, dependency directories, and build output. Verify process identity and stop only task-owned processes before removal. Preserve required screenshots, reports, CONTEXT.md recovery notes, and unresolved MISTAKES.md handoffs outside disposable worktrees. Inspect untracked and ignored files as well as tracked files; classify secrets and user files for preservation, not publication. Remove known disposable task output through safe path-scoped operations, then use normal Git worktree removal. Do not use force deletion to bypass unknown or uncommitted work.

Removing an eligible worktree also recovers its local dependency and build directories. Do not clear shared package caches, shared databases, global installations, or another team's resources to inflate reclaimed space. Remove a clean idle integration worktree when no queued/unfinished integration needs it; otherwise reuse that one worktree and record the retention reason. Do not create a new integration worktree per feature.

Confirm from the cleanup helper's result that each intended path and process is gone and the Git worktree list is correct. Record team ID, release identity, removed resources, retained resources with reasons, and reclaimed disk space when supported by a practical before/after measurement. Do not invent a disk-space figure. Mark Cleanup complete only when all eligible resources are removed; open one bounded cleanup issue for failures, preserve the production-success record, and retry only with new evidence. Future resume includes pending cleanup. Never delete unfinished feature work merely to reduce the number of worktrees.
