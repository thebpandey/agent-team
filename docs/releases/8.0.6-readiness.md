# Agent-Team 8.0.6 release readiness

Version 8.0.6 fixes the native Windows delivery gap. The release publishes Linux amd64 and Windows amd64 downloads. It does not claim a published macOS binary.

## Download contracts

- Linux amd64 remains the strict four-file distribution: `agent-teamctl-8.0.6.zip`, `RELEASE.json`, `SBOM.cdx.json`, and `SHA256SUMS`. Its checksum file has exactly the three existing entries.
- Windows amd64 is one `agent-teamctl-8.0.6-windows-amd64.zip` download with a matching `.sha256` sidecar. One extraction exposes `agent-teamctl.exe`, the strict canonical release files, and the inner archive.

## Publication gates

The manual `vnext-release` workflow must pass for the exact main commit before creating the annotated `v8.0.6` tag and GitHub release. Source metadata remains a candidate until this workflow completes; this document does not substitute for its evidence.

1. Run Phase 1–5 checks and bind their records to the release revision and source digests.
2. Run `go test ./... -count=1` and `go vet ./...` on Linux, macOS, and Windows.
3. Package with `go run ./cmd/vnext-release package --version 8.0.6 --commit "${GITHUB_SHA}"`; verify both Linux canonical assets and the Windows bundle, manifests, SBOMs, checksums, allowlist, and deterministic archive bytes.
4. Confirm the Windows binary is an amd64 PE executable and the Linux archive remains readable by the strict v8.0.5-compatible parser.
5. On a Windows runner, verify the outer sidecar, extract the Windows bundle once, and run `agent-teamctl.exe install --host both --json` without WSL.
6. Run packaged Linux Codex and Claude canaries, cutover, rollback, provider verification, and revision-bound readiness evidence.
7. Publish the verified assets under the new tag and confirm GitHub Pages serves version 8.0.6 with working release links.

Native install and update must reject an unowned or symlinked same-name Codex discovery root before changing the target. The result reports the exact conflicting `SKILL.md`; the operator moves its whole root to a recoverable backup outside discovery paths and retries. A manifest-owned top-level entrypoint remains eligible for the existing migration path.

## Recovery and scope

The native runtime and worker contract are unchanged. Manifest-owned update, rollback, and uninstall retain changed or unknown user files. Existing v7 migration requirements, native host-home handling, and optional-tool limitations remain as documented for [8.0.5](8.0.5-readiness.md).
