## Why this repair was needed

Published 8.0.11 passed its release workflow, but an actual managed update
failed with `revision: lifecycle journal budget exceeded`. The downloaded
binary exceeded the old installation-journal allowance. The update did not
complete: the old 8.0.10 manifest remained at revision 5, and all four owned
file hashes still matched it. The published 8.0.11 artifacts are immutable.

The [repair architecture](../architecture-8.0.12.md) explains the bounded
schema-1 journal changes. The limits are 32 MiB per file and 64 MiB
for the aggregate journal; package validation, ownership, rollback, and
unknown-file preservation remain required. No background agent service or new
host hook is introduced.

## Release checks

The completed release and installation followed these gates:

1. Test the committed installer with measured executable sizes around 14 MiB
   on both sides of an update. Cover successful update, recovery, rollback,
   oversized rejection, and preservation of modified or unknown files.
2. Run native tests and vet on the required platform matrix. Verify current
   version authority, host skill metadata, release manifest, and SBOM.
3. Build the actual release artifact and run its managed-update canary against
   a prior installation. Small synthetic binaries alone do not qualify this
   repair. Verify the resulting installed manifest and exact owned hashes.
4. Verify archive checksums, Windows bundle layout, readiness, rollback, and
   provider evidence against the release revision before publishing.
5. After publication, download and verify the assets again, complete the
   separately authorized managed update, and rerun setup/status smoke checks
   against the installed controller. Only then update current-release Pages
   and installation claims.
